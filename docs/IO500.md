# IO500 on atlas-native

[IO500](https://io500.org/) is the HPC storage benchmark WEKA and other parallel filesystems
publish: bandwidth phases (IOR "easy" large sequential files per process, IOR "hard" small
interleaved writes to one shared file), metadata phases (mdtest "easy" and "hard" creates, stats,
reads and deletes), and a parallel find, combined into one score. Atlas ships a harness that runs
the unmodified suite against an atlas-native filesystem ([`NATIVE_FS.md`](NATIVE_FS.md)) through
the FUSE client.

**Status:** the harness runs the full suite end to end on the lab k3s. There is **no IO500
submission and no representative number yet**: that needs the NVMe and RDMA benchmark hardware
the roadmap lists as a prerequisite ([`NATIVE_STORAGE.md`](NATIVE_STORAGE.md)). The lab results
below show that the harness works, not how fast atlas-native is.

## What is in the repo

| Piece | Role |
|---|---|
| `Dockerfile.io500` | Image `atlas-io500`: IO500 at the SC26 release (`io500-sc26_v1`, IOR and pfind at the commits its `prepare.sh` pins) built against Debian's Open MPI, plus `atlas-native-mount` |
| `deploy/io500/io500-run.sh` | Entry point: mounts `IO500_FS`, writes the IO500 config, runs `mpirun -np $IO500_NP io500`, deletes its data and unmounts |
| `scripts/io500-native-remote.sh` | Builds the image on a k3s host, creates a scratch filesystem in an `atlas-native` release, runs the pod, copies the results back and removes the pod and filesystem |

The benchmarks are separate programs built from upstream sources (IO500: MIT, IOR/mdtest:
GPL-2.0, pfind: LGPL-3.0); nothing in Atlas links them, and they ship only in this benchmark image.

## Running it

Against an existing `atlas-native` release (plain-HTTP API; `httpTls` releases are not supported
by the script yet):

```sh
scripts/io500-native-remote.sh <host> <user> --namespace atlas-native --np 16
```

Results land in `io500-results/<timestamp>/` (IO500's `result.txt`, per-phase logs and CSVs, the
config). Options map to the entry point's environment: `--np` (`IO500_NP`), `--stonewall`
(`IO500_STONEWALL`), `--ior-easy-block`, `--ior-hard-segments`, `--mdtest-easy-n`,
`--mdtest-hard-n` (phase sizes), `--mount-args` (extra `atlas-native-mount` flags, e.g.
`--cache-leases` or `--direct-reads`) and `--node` (pin the pod to a node).

Without options the run uses IO500's rules: a 300 s stonewall on every write phase and phase sizes
large enough not to finish before it. Anything smaller makes IO500 mark the run `[INVALID]`, which
is right for a functional check and wrong for a published number.

The image can also run on its own (any container runtime with `/dev/fuse` and privileges to
mount):

```sh
docker run --rm --privileged --device /dev/fuse \
  -e ATLAS_NATIVE_ENDPOINTS=http://node-0:7480,http://node-1:7480,http://node-2:7480 \
  -e ATLAS_NATIVE_TOKEN_FILE=/token -v $PWD/token:/token:ro \
  -e IO500_FS=bench -e IO500_NP=32 -v $PWD/results:/results atlas-io500
```

### Caches

IO500 expects the client's page cache to be dropped before each phase when readers and writers
share a node. `IO500_DROP_CACHES=1` does that (`echo 3 > /proc/sys/vm/drop_caches`), which drops
the **host's** cache for every tenant: use it only on a dedicated benchmark host. Without it, read
phases on a single client node can be served from cache and overstate read bandwidth.

## Requirements for a submission

- **Hardware:** NVMe data devices on the storage nodes (`io_uring` device backend,
  [`NATIVE_NODE.md`](NATIVE_NODE.md)), a fast network, and separate client nodes. IO500's
  10-node lists, the ones vendors usually compare on, need ten client nodes.
- **Several client nodes:** the harness runs every rank in one pod. A multi-node run needs MPI
  across pods (for example the Kubeflow MPI Operator launching this image on every client node,
  each mounting the same filesystem); the entry point's config and mount logic stay the same.
- **Rules:** 300 s stonewall, default phase definitions, caches dropped where needed, and IO500's
  reproducibility questionnaire filled in for the run.

## Lab run (functional only)

On the lab k3s host (one storage node on the host's shared HDD, replication factor 1, other
tenants' load average around 7–25 during the run), with 4 ranks in one pod, a 30 s stonewall and
small phases (`--ior-easy-block 256m --ior-hard-segments 2000 --mdtest-easy-n 2000
--mdtest-hard-n 1000`), IO500 completed every phase, and Atlas cleaned up the data, pod and
filesystem afterwards. IO500 marked the run `[INVALID]` because of the short stonewall and runtime.

What the run showed:

- **Every phase works through the FUSE client**: large per-process files, the shared-file
  interleaved IOR pattern, creates, stats, reads and deletes in per-rank and shared directories,
  and pfind's parallel tree walk (565 entries checked, no errors).
- **Metadata writes are bound by synchronous disk latency on this host.** A single synchronous
  4 KiB write on the host's disk took about 78 ms (`dd oflag=dsync`), and every create and delete
  commits through the Raft log, so mdtest-easy reached about 9 creates/s and 6 deletes/s, and
  mdtest-hard about 1 create/s (68 ms per file across 4 ranks; each file is created, written and
  closed). Stats and reads, which don't commit, ran at 16–29 thousand per second.
- **find matched nothing**, which IO500 flags: in 30 s each rank created only about 19 "hard" files,
  and none of their names contains the `01` pattern find searches for. With rule-sized phases this
  doesn't happen.

These figures describe the lab disk, not atlas-native on NVMe. The next step for this benchmark is
the benchmark hardware, and with it a multi-node run.
